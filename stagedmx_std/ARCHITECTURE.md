# stagedmx_std 控台固件 —— 逻辑图与"发送失败"排查结论

> 用途：把控台固件的**任务/核/数据流**画清楚，并回答一个具体问题：
> **`stagedmx_bustest`（双宇宙互发自检）和 `stagedmx_sniff`（灯具模拟器）会不会导致控台"发送失败"？**

---

## 一、结论（先给答案）

**固件层面：不会。** 三个工程是三块独立的固件，各自跑在自己的板子上：

| 工程 | 烧在哪 | 与控台的关系 |
|---|---|---|
| `stagedmx_std` | 控台（COM7） | 本体 |
| `stagedmx_sniff` | 第二块板（COM3） | 只是**挂在总线上的一个监听/应答设备**，控台的发送循环**不依赖它** |
| `stagedmx_bustest` | 只有被烧进**控台**时才运行 | 它是一支"替换固件"，**当前不在控台里**，不影响任何东西 |

控台的发送循环是自足的：`dmx_write()` 把帧交给 UART 驱动，`dmx_send()` 启动硬件发送。
**它不读总线、不等任何外部设备**，所以别的板子/工程**改不了控台的 `fail` 计数**。

**电路层面：会，而且这是当前故障的机理。** 见第三节。

### 关键设计（都是踩过坑换来的）

1. **DMX 输出任务钉 core 1、优先级 6**：输出绝不能被 BLE/Wi-Fi 抢占；
   控制台打印、状态灯、USB 都放在 core 0 或独立任务里，**谁都不许进 DMX 任务**。
2. **中断跟着"安装它的核"**：`dmx_init` / RDM 结束后的重装**必须都在 core 1**，
   否则 `esp_intr_alloc()` 把 UART/GPTimer 中断搬到 core 0 ⇒ 恒超时、该宇宙再也不发。
3. **暂停只停在帧边界**：中途停会把驱动留在 `DMX_STATUS_SENDING`，之后 `dmx_send` 恒返回 0。
4. **版本号乐观并发**：效果层每 10ms 整帧提交，但推子/App 刚写进来的值不会被覆盖。

## 三、"发送失败"到底是谁的责任 —— 分三层看

| 层 | 表现 | 谁能影响它 |
|---|---|---|
| **① 固件发送状态**（遥测 `fail`）| `dmx_send()` 返回 0 / `dmx_wait_sent()` 超时 | **只有控台自己**（驱动/中断/任务被堵）。别的板子改不了 ✗ |
| **② UART 引脚上有没有数据** | 用示波器/第二块板直连测 | 控台固件 + 引脚配置（**引脚错 = 收发全灭**，我们经历过）|
| **③ 总线（A/B）上是不是干净** | 接收端能不能解出合法帧 | **物理拓扑**：一条线上有几个驱动源、A/B 极性、终端电阻 |

**最容易被误读的一点**：遥测里的 `fail=0` 只证明 **MCU 把字节推出去了**（第①层），
**它看不见第③层** —— 总线上两个驱动源互打时，UART 依然是 `ok=1 fail=0`。
所以"遥测全绿但灯收不到"是**完全成立**的组合。

### 具体会互相破坏的三种接线

1. **两个宇宙的 A/B 并在一起**（当前状态）
   两个宇宙是**并行发送**的两个独立任务（各 512 通道、各 ~41fps），
   ⇒ 一条总线上**永远有两个驱动源互打** ⇒ 接收端拿到的是残帧/乱码。
   ⇒ 现场表现："灯完全不受控 / 显示未连接"。
   **修法：两个宇宙各自一条 A/B 线**（或只保留要用的那一个）。

2. **第二块板（模拟器）的 485 若 DE 停在发送态**
   它就是**第三个驱动源** ⇒ 更彻底地压垮总线。
   它作为"灯具"本应常驻**接收态**（DE=0，`/RE`=0），
   但这点**必须实测**（量它的脚3，应为 0V）。

3. **RDM 扫描期间**
   `dmx_rdm_mode(true)` 把被扫宇宙的 EN 交给 UART RTS 并按收发翻转，
   同时该宇宙**暂停发送** ⇒ 若另一个宇宙还在发，总线上仍是两个驱动源
   ⇒ 这就是"点 RDM 扫描时灯有动作/复位"的机理。
   **RDM 要在**真正独立**的总线上做**。

### 另一个历史性风险开关

`dmx.c` 顶部有编译期开关 `DMX_RECLAIM_PINS`：关闭时 RDM 结束后**不收回**被
UART 借走的 RX/EN ⇒ 表现为"扫过一次 RDM 后该宇宙永久不发"。
**现有配置为打开**，请勿随意关闭（对照实验除外）。

## 四、验收/自检工具

| 工具 | 做什么 | 判据 |
|---|---|---|
| `stagedmx_bustest`（烧到控台） | 两个宇宙**互发互听**，逐通道校验 512 个通道 | `RESULT ... bad=0 OK` = 发送+接收+通道映射全对 |
| `stagedmx_sniff`（烧到第二块板） | 当"真灯"：收帧解析 + RDM 应答 + 板载 RGB 显示 ch1/2/3 | RGB 跟着推子变色 = 通了 |
| 控台 LED（GPIO1） | 常亮=正常 / 1Hz=BLE 未连 / 2Hz=驱动异常 / 5Hz=发送失败 | 一眼看运行状态 |

## 五、当前实测状态（2026-10 调试记录）

- 控台：`U1/U2 frm=.. fps=41 ok=1 fail=0`、BLE 连着、App 推的值到达 ✓
- 引脚（**按实际接线，勿再对调**）：U1 `DI→17 / RO→18 / DE→4`、U2 `DI→16 / RO→15 / DE→5`
  - ⚠ 曾在固件里把 TX/RX 对调过，结果 MCU 的 TX 接到了芯片的 RO（两输出对打）
    ⇒ 收发全灭、线上只剩噪声。**改引脚前后都要跑 `stagedmx_bustest` 验证 bad=0。**
- 未闭环：第二块板走差分 A/B 时收到的是"错帧"（有活动、无合法帧），
  与"两个宇宙 A/B 并接 + 可能存在的第三个驱动源"一致 ⇒ 先把总线拆干净再测。
